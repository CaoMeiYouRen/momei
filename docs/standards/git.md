# Git 工作流规范 (Git Workflow Standards)

## 1. 分支管理策略 (Branching Strategy)

项目采用“稳定主线 + 按需集成分支/任务分支”的模式，优先保证主干清晰、任务边界明确，而不是为每一类工作长期维护固定分支。

| 分支名称 | 职责描述 | 工作树目录 (示例) |
| :--- | :--- | :--- |
| `master` | **主分支**：用于稳定代码、版本发布与最终合并结果。 | `momei` (主目录) |
| `dev` | **开发集成分支（可选）**：当团队需要集中承接阶段性功能联调时使用。 | `../momei-dev` |
| `test` | **测试验证分支（可选）**：当需要隔离自动化测试、回归验证或实验性验证时使用。 | `../momei-test` |

补充约束：

- 不再为 `fix`、`docs` 维护长期专用分支。修复类、文档类或小范围治理类工作，优先直接在当前任务分支或当前协作分支中完成。
- 若某项工作确实需要隔离，应创建短生命周期任务分支，而不是把分支类型当作长期目录分类。

## 2. Git Worktree 规范

`git worktree` 是推荐的效率工具，但不是强制前提。是否使用，应根据任务并发度、磁盘成本、依赖体积与团队协作方式决定。

适合使用 Worktree 的场景：

- 需要并行维护多个长时间存在的分支上下文。
- 需要减少频繁切分支带来的依赖重装、构建缓存失效或上下文切换成本。
- 需要把开发、测试或发布验证放在相互隔离的工作目录中。

不强制使用 Worktree 的场景：

- 单人或小范围任务，当前仓库切分支成本可接受。
- 文档修订、轻量修复、单点验证等短平快改动。
- 当前阶段没有并行维护多分支的必要。

### 2.1 目录命名规范
- 若使用 Worktree，推荐将目录放在项目主目录的同级。
- 推荐采用 `momei-` 前缀 + 分支名或任务名进行命名。
- 例如：`../momei-dev`, `../momei-test`, `../momei-feature-search`。

### 2.2 创建工作树
示例：
```bash
git worktree add ../momei-dev dev
git worktree add ../momei-test test
git worktree add ../momei-feature-search feature/search-improvements
```

### 2.3 工作树维护与清理
- **定期同步**：各工作树应定期执行 `git pull --rebase` 保持与远程同步。
- **及时清理**：对于临时创建或不再使用的工作树，必须使用规范命令移除，严禁直接手动删除目录：
  ```bash
  # 安全移除工作树
  git worktree remove ../momei-temp-branch
  # 清理过期的 Git 元数据
  git worktree prune
  ```

## 3. 合并与集成 (Integration)

- **提交前 Review 前置**：任何改动在进入 commit 之前，都必须先经过至少一轮 review；代码、配置、脚本、规划与文档改动均不例外。
- **未闭环不得提交**：若 review 已指出问题但尚未形成明确的修复结论、通过条件或关闭记录，则不得继续 commit 或发起合并。
- **合并方向**：所有特性开发完成后，应基于当前协作策略向 `master` 或当前启用的集成分支发起合并请求（Pull Request / Merge Request）。
- **合并门槛**：合并仅限可信提交者且 CI 通过；作者判定、issue / PR 处置与机器人 PR 口径见 §6。
- **同步原则**：当 `master` 或当前集成分支发生重大更新后，其他活跃分支或工作树应及时同步、合并或重定位 (Rebase) 到最新基准点。

## 4. AI 智能体行为准则

- **分支感知**：AI 代理在执行任务前必须检查当前工作目录所属的分支。
- **按需切换**：若当前任务明确需要独立验证环境，可优先检查是否已有合适的 Worktree；若不存在，也可以继续在当前仓库内完成，不强制新建 Worktree。
- **环境隔离**：使用多个工作树时，不同目录的环境配置（如 `.env`）应保持逻辑一致但环境隔离，避免相互干扰。
- **推送默认关闭**：AI 代理在 `git commit` 后默认**不**执行 `git push`。仅当用户明确发出"推送""push""推到远端""push to remote"等指令，或命中 §7 的授权例外时方可推送；推送后应告知结果与目标分支。

## 5. 提交钩子与历史改写陷阱

| 陷阱 | 结论 |
|:---|:---|
| `lint-staged` 的 `git add` | 钩子会把当时**未暂存**的改动一并 stage（可能把另一批文件或无关脏文件卷进本笔）；`*.md` 规则里的裸 `git add` 等价 `git add -A`，是最常见来源——先提交文档批次或给 `git add` 指定路径。拆分提交后必须按 `git show --numstat` **实测落库**回填拆分表，不要按计划口径写；必要时提交前 `git stash push -- <path>` 隔离无关脏文件。 |
| `lint-md --fix` 顺带 stage | pre-commit 会重排被覆盖的 Markdown 并 stage；若该文件不属于本批，会把无关文档卷进提交。拆分时把含该文档的那一批**先提交**，后续批次的钩子对其即无操作。 |
| 多段提交信息的换行 | shell 双引号里的 `\n` 不会转义（bash 只在 `$'...'` 中解释），会写入字面 `\n`；一律用 `git commit -F <file>` 或 heredoc。 |
| 改写已有提交信息 | 用 `git filter-branch --msg-filter` 修正时，range 起点必须取「**最后一个不受影响的提交**」；从更早的祖先起算会连带重写历史，使文档中引用的哈希失效。 |
| 依赖 PR 的清理顺序 | ① 先修 master 自身红灯（否则 PR CI 结论不可信）→ ② 依赖 PR 走 `@dependabot rebase` + 自动合并 → ③ 人工 PR 最后逐个 rebase 并重解析锁文件。每次合并都会让其余改锁文件的 PR 失效，故人工 PR 不要提前 rebase。 |

## 6. GitHub 协作与可信提交者 (GitHub Collaboration & Trusted Committers)

> 背景与决策见 [2026-11-12 GitHub 协作边界与推送授权治理](../design/governance/2026-11-12-github-collaboration-and-push-authorization.md)。

### 6.1 可信提交者

- 允许合并的提交仅来自：项目所有者（`OWNER`）、项目贡献者（`MEMBER` / `COLLABORATOR`），以及本书登记的受信机器人：`dependabot[bot]`、`dependabot-preview[bot]`、`dependfix[bot]`。
- 判定以 GitHub 返回的 `author_association` 与 `user.type` 配合上述清单为准，不得仅凭昵称或头像推断来源。
- 新增受信机器人须先在本书登记，未登记的机器人按外部来源处理。
- 不可信来源的 PR 可以审查、评论、关闭，但不得合并。

### 6.2 Issue 处置

| 来源 | 默认动作 |
| :--- | :--- |
| 项目所有者 | 调研确认后评估 ROI，可进入 `docs/plan/backlog.md` |
| 外部提交者 | 只做调研；核实后给出简要反馈，问题成立则保留并等待开发者审批，不成立则关闭并写明依据 |

- Issue 默认只做调研，不直接进入实现。
- 外部 issue 进入 `docs/plan/backlog.md` 必须经项目所有者审批。

### 6.3 PR 处置

- 无论来源，PR 都必须审查，并给出保留开放 / 关闭 / 合并的明确结论与依据。
- 仅可信提交者的 PR 允许合并；合并前要求 CI 通过、无冲突、非 draft。
- `dependabot[bot]` / `dependabot-preview[bot]` 的依赖升级 PR 在命中 [`.github/mergify.yml`](../../.github/mergify.yml) 规则（`Test` 通过 + `dependencies` label + 受信作者）时走 Mergify 自动合并，依赖升级引入的风险由 CI 门禁承担。
- 未命中 Mergify 规则的机器人 PR（含 `dependfix[bot]` 及其余机器人）按常规 PR 审查、修复（rebase / 锁文件重解析）后合并。
- 对可信提交者的 PR，允许为解决冲突或修正明显错误做简单修改后合并；复杂修改回到常规流程（短生命周期分支 + 审查 + CI）。
- 不可信来源 PR 的改动不得以直接 cherry-pick / 重新提交的方式绕过合并门槛；需由可信提交者重新提交并重走 review。
- 关闭 PR 必须写明理由：已由 `master` 覆盖 / 重复 / 无效 / 需重新提交。

### 6.4 上游联动

- 依赖作者为 `CaoMeiYouRen` 的包，确认问题确实来自该包时，可在查重后向上游提交 issue；内容须符合上游项目规范，并提供最小复现。
- 与上游 / 下游项目存在协作关系时，同样通过 issue 反馈问题。
- 提交上游 issue 前必须由用户审查并授权；代理只负责起草与查重，不直接创建。

### 6.5 阶段规划联动

- 开始下一阶段规划时，先拉取最新 issue、PR 与 Actions 状态，评估其中对规划有影响的内容，必要时纳入下一阶段。

### 6.6 重复评论抑制

- 已评估过的 issue / PR，若无新活动（新评论、新提交、状态变化），不重复 comment。

## 7. 推送授权 (Push Authorization)

默认不推送（见 §4）。以下三类例外允许代理主动推送，其余场景仍需用户显式指令。

### 7.1 修复 CI 时推送

- 目的仅是让改动触发 CI，以验证修复是否生效。
- 推送后必须等待该次 run 给出结论再决定下一步；结论未出前不得再推送新的修复。
- 同一时间至多只有一个修复批次处于 CI 验证中，不得把多个未验证修复串联推送。
- 连续 3 次修复仍不通过时停止，记录失败点与已试方案，转人工判断。

### 7.2 完整条目完成后推送

- 一个完整条目完成后可以推送，但不作为默认动作；建议积累若干条改动后一次推送。
- 推送前完成本地必要验证（`lint` / `typecheck` / 定向测试 / 相关构建），长耗时检查可跳过并登记。
- 推送后监控 CI 状态；CI 失败时按 §7.1 处理。

### 7.3 风险隔离分支

- 改动可能影响项目整体运行状态，或改动规模较大时，开短生命周期分支并通过 PR 提交，CI 通过后合并回 `master`。
- 合并后清理对应分支与工作树。

### 7.4 定时任务的适用方式

- 定时任务受本节约束，"已授权推送"不等于"每次改动都推送"；修复 CI 时按 §7.1，完整条目按 §7.2，高风险改动按 §7.3。
